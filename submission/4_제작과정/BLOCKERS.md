# 막힌 지점과 해결 과정

> 결과물만 보면 안 보이는 부분이다. **증상 → 어떻게 찾았나 → 원인 → 해결 → 배운 것** 순서로 적는다.
> "어떻게 찾았나"를 비우면 안 된다. 거기가 실제로 시간을 쓴 자리다.
> 원천 기록: `docs/07_DEPLOYMENT.md §1.5–1.7` · `docs/DECISIONS.md` · `docs/LOG.md`

## 1. Chrome에서만 흰 화면 (데모 치명 버그였다)

- **증상**: 배포한 Console이 사파리에서는 정상인데 **Chrome에서만 백지**. `curl`로 받으면 HTML도 정상.
- **어떻게 찾았나**: "브라우저 문제"로 넘길 수 있었지만, Chrome 개발자도구 Network를 열어 `net::ERR_INVALID_CHUNKED_ENCODING`을 확인했다. 응답이 오는데 **끝나는 신호가 유실**되고 있었다.
- **원인**: Next.js가 자체 gzip을 하고 Railway 엣지가 다시 압축하면서 chunked 전송의 **종료 청크가 깨졌다.** 사파리는 관대해서 렌더했고 Chrome은 규격대로 버렸다.
- **해결**: `next.config.ts`에 `compress: false` — 압축은 엣지에 맡긴다.
- **배운 것**: **브라우저 하나만 보고 "된다"고 판단하면 안 된다.** 심사위원 대다수가 Chrome이다. 사파리에서 멀쩡한 화면이 Chrome에서는 백지였다. 이후 모든 확인은 Chrome + 사파리 + 모바일 3종으로 한다.

## 2. 사내망에서 배포 플랫폼 대시보드 자체가 안 열림

- **증상**: 사내 노트북 Chrome에서 railway.com(로그인 페이지까지 전부) 백지. **배포된 우리 앱 3개는 정상** — 그쪽은 1번으로 이미 해결된 상태였다.
- **어떻게 찾았나**: ① 인증서 발급자를 확인했더니 `Forward Trust CA` — 사내 보안장비가 TLS를 열어보고 있었다. ② 휴대폰 테더링으로 바꿔도 그대로였다 → VPN이 모든 트래픽을 회사로 되돌려 보내고 있었다(터널). ③ **Render·Fly·Vercel도 같은 증상**임을 확인했다.
- **원인**: 사내 SSL 검사 장비(Palo Alto SSL Forward Proxy)가 복호화·재암호화하면서 chunked 응답을 깨뜨린다. 검사는 **망을 따라오는 게 아니라 노트북을 따라온다.**
- **해결**: ③에서 **"플랫폼을 옮기는 건 해결책이 아니다"**가 확정됐다. 우회 3단으로 정리 — ① 사파리(관대함) ② 휴대폰 브라우저(VPN 없는 유일한 경로, CLI 로그인 승인에 사용) ③ IT 티켓(근본). **일상 운용은 CLI로 전환**했다 (CLI↔API 통신은 검사망 아래서도 정상).
- **배운 것**: 막혔을 때 **"다른 서비스로 갈아탈까"는 원인을 모를 때 나오는 선택**이다. 세 플랫폼에서 재현해 보고 나서야 갈아타도 소용없음을 알았다. 그리고 사내 환경 제약은 회피 대상이 아니라 **기록해서 팀이 공유할 조건**이다.

## 3. push해도 배포가 안 됨 — 실패도 아니고 아무 일도 없음

- **증상**: 몇 시간째 배포본이 옛 커밋. Deployments 목록에 **새 항목이 아예 생기지 않음** (실패 표시도 없음).
- **어떻게 찾았나**: 빌드 로그를 아무리 봐도 없는 로그는 못 본다. "실패가 아니라 시작조차 안 했다"로 관점을 바꿨더니 볼 곳이 Source 설정으로 좁혀졌다.
- **원인**: **레포 연결이 끊어져 있었다** (레포 이름을 바꾼 시점과 겹쳤다).
- **해결**: Disconnect → Connect 재연결. 그 직후 `'$PORT' is not a valid integer` 크래시 루프 → 재연결로 Dockerfile 빌드가 되살아나자 **예전에 넣어둔 대시보드 Start Command가 셸 없이 실행**되며 `$PORT`가 안 풀린 것. Dockerfile을 쓸 때는 Custom Start Command를 **비워둔다.**
- **배운 것**: **"에러가 없다"는 정상이 아니다.** 아무 일도 안 일어나는 것이 가장 늦게 발견되는 고장이다.

## 4. 첫 배포에서 연달아 막힌 4개 (같은 데서 또 막히지 말 것)

| 증상 | 원인·해결 |
|---|---|
| "could not determine how to build" | Root Directory 미설정. **`/backend`처럼 슬래시를 붙여야** 인식됐다 |
| "No start command detected" | `railway.json`·Dockerfile을 무시하고 빌드. Start Command를 대시보드에 직접 입력 |
| "Application failed to respond" | 도메인이 보는 포트 불일치. 플랫폼이 주는 `$PORT`는 **8080** |
| 프론트 빌드 실패 (EBADENGINE) | Node 18이 선택됨 → `package.json`에 `engines.node >= 20` 명시 |

- **배운 것**: 배포는 "코드가 되면 되는 일"이 아니다. 그래서 **빈 껍데기 단계에서 먼저 배포**하도록 계획을 바꿨다(WBS 0.4를 8/24 → 8/17로 앞당김). 코드가 적을 때 붙이는 것이 가장 싸다.

## 5. API 키 없이 1,118개 문단을 써야 했다

- **증상**: 합성 코퍼스를 63건에서 320건(인사이트 단위 1,118)으로 늘리기로 했는데, 본문을 LLM으로 생성하면 ① 실행마다 결과가 달라져 **재현이 안 되고** ② 팀원 3인이 각자 API 키를 준비해야 한다.
- **어떻게 찾았나**: "생성"을 "조립"으로 바꿔 생각했다. 의료진 발언은 자유 작문이 아니라 **정해진 몇 가지 골격에 세부만 갈리는** 형태다.
- **해결**: **조합형 산문 엔진** — 손으로 쓴 문장 조각(골격 × 세부 × 잡음 문장)을 시드 고정 난수로 조립한다. LLM 호출 0회, 같은 시드 → **바이트 단위로 같은 코퍼스.**
- **배운 것**: 재현성이 필요한 데이터는 **모델이 아니라 규칙으로** 만드는 게 낫다. 부수 효과로 검증(V2 재현성)이 공짜가 됐다.

## 6. 코퍼스 검증이 6번 연속 실패

각각 다른 원인이었고, 검증 스크립트가 없었다면 전부 그냥 넘어갔을 것들이다.

| 실패 | 원인 | 조치 |
|---|---|---|
| 조합 수 부족 (39개 필요, 35개 가능) | 조각 풀이 얕았다 | 세부·골격 풀 확장 |
| 신호 개수 불일치 (32 ≠ 27) | 한 발언에 두 신호가 겹칠 때(co-located) **이중 계산** | 겹침 수를 빼고, 검증 기준을 "독립 의료진 수 이상"으로 정정 |
| 같은 문장이 두 문서에 등장 | 조각 풀을 따로 호출해 충돌 | 전역 중복 방지 집합 도입 |
| **미래 날짜** (2026-08-26) | 오늘 이후 날짜가 생성됐다 | 마지막 날짜를 상한으로 고정 |
| 문단이 반복적으로 읽힘 | 같은 도입부·같은 위치에 신호 배치 | 도입부 확률화 + 신호 위치 무작위화 + 이름 충돌 검사 |
| 문서 하나에 같은 이름 두 번 | 이름 풀에서 중복 추출 | 문서 내 이름 충돌 검사 추가 |

- **배운 것**: 합성 데이터는 **"만들었다"가 끝이 아니다.** 각본과 결과가 일치하는지 검증하는 코드가 데이터 생성기보다 중요하다. 위 6개 중 5개는 눈으로 읽어서는 못 찾았다.

## 7. "경쟁사 분석"을 넣으려다 규정과 정면충돌

- **증상**: 화면을 더 유용하게 만들려고 **개별 의료진의 처방량 API + 제약사 지급내역 DB(Open Payments) 연결**을 검토했다. 사업적으로는 가장 매력적인 기능이었다.
- **어떻게 찾았나**: 우리가 스스로 못 박은 절대 규칙 #7("개별 의료진 처방성향 점수화 금지")과 정면으로 부딪혔고, 반부패 규제 리스크도 있었다. 게다가 화면은 가명으로 표시하는데 외부 DB와 결합하면 **가명이 풀린다.**
- **해결**: 기능을 버리지 않고 **축을 뒤집었다.** 개인 → **제조사·시장 단위 공개 집계**. 허가 연령 지도(공개 라벨), 경쟁사 시험 등록 타임라인(공개 등록부), 문헌 추이. 개인 식별 0건, 예측선 없음.
- **배운 것**: 규칙과 부딪히는 요구는 **버리는 것과 우기는 것 사이에 세 번째 길**이 있는 경우가 많다. 어느 축으로 집계할지를 바꾸면 같은 질문에 답할 수 있었다.

## 8. 권한을 열면 규칙이 깨지고, 막으면 기능이 죽는다

- **증상**: 7번의 시장 화면은 상업 담당(`COMMERCIAL`)이 봐야 의미가 있다. 그런데 그 역할은 미승인 적응증(Development) 관련 정보를 볼 수 없게 막아 두었다. 권한을 열면 규칙 #5가 깨지고, 막으면 화면이 무용지물이다.
- **어떻게 찾았나**: "권한 조건을 어떻게 잘 쓰나"를 고민하다가, **조건문은 언젠가 실수로 빠진다**는 점에서 접근을 바꿨다.
- **해결**: **테이블을 나눴다.** 시장 참조 데이터는 `external_refs`에 넣고, 이 테이블에는 **가설을 가리키는 컬럼 자체를 두지 않았다.** 조건문을 잘 쓰는 게 아니라, 연결할 방법이 **구조적으로 없게** 만든 것이다. 가설과 연결된 근거는 별도 테이블에 두고 거기에 게이트를 건다. 회귀 테스트 1개를 의무화했다.
- **배운 것**: 규칙을 지키는 가장 안전한 방법은 **어길 수 있는 경로를 없애는 것**이다. 검토로 막는 것은 언젠가 뚫린다.

## 9. 우리가 만든 화면이 우리 규칙을 어기고 있었다

- **증상**: 실행 루프를 보여주는 카드를 만들었는데, **전문조직 검토로 넘긴 항목이 "현장에서 수집 완료"로 표시**되고 있었다.
- **어떻게 찾았나**: 화면을 만든 직후 상태 머신 정의와 대조했다. `COLLECTED`는 현장 체크리스트 항목에만 있는 전이인데, 검토 요청 항목에도 붙여 놓았다.
- **원인**: 4단계를 예쁘게 맞추려고 두 종류의 액션에 같은 진행 단계를 썼다.
- **해결**: 검토 요청 항목의 마지막 칸을 "검토 중 / 수집 귀속 개념 없음"으로 바꿨다. 화면과 문서 양쪽을 고쳤다.
- **배운 것**: 이걸 놓치면 "전문조직에 넘긴 것"이 "현장에서 확인된 것"으로 집계된다. **연출을 위해 상태를 하나로 합치면 숫자가 거짓이 된다.**

## 10. 목업이 배포본에 없었다

- **증상**: 팀에 "배포본에서 확인하세요"라고 공유했는데 링크가 404.
- **원인**: 목업 파일이 `demo/`에 있었고, 배포 서비스의 root directory는 `apps/console`·`apps/field`·`backend` 세 곳뿐이었다. **어느 서비스에도 포함되지 않는 위치**였다.
- **해결**: `apps/console/public/draft.html`로 복사해 `/draft.html`로 서빙. 두 파일이 바이트 동일해야 하므로 **목업 수정 시 같은 커밋에서 재복사**하는 규칙을 문서에 못 박았다.
- **배운 것**: **"로컬에서 열린다"는 배포됐다는 뜻이 아니다.** 공유 전에 배포 URL로 직접 눌러 본다.

## 11. 폴더 이름이 한글이라 자동 분류가 통째로 무력화

- **증상**: 개발 일지 자동 생성기가 `submission/` 폴더를 13개나 건드린 커밋을 "문서 작업"으로 분류했다. 값이 **그럴듯했다** — 그 커밋이 문서도 건드렸으니까.
- **어떻게 찾았나**: 생성된 표를 그대로 믿지 않고 커밋의 파일 목록을 직접 세어 봤다. `"submission/4_제작과정/..."` — 경로가 **인용부호와 8진 이스케이프**로 나오고 있었다.
- **원인**: git 은 비ASCII 경로를 기본으로 인용해서 출력한다(`core.quotepath`). 우리 제출 폴더 이름은 **전부 한글**이라 경로로 시작하는 모든 판정이 실패했다.
- **해결**: `git -c core.quotepath=false` + 인용부호 제거.
- **배운 것**: **자동 생성물은 한 번은 손으로 검산해야 한다.** 틀린 값이 오류로 나오면 금방 잡히지만, **그럴듯한 값으로 나오면 영영 모른다.** 이건 우리 제품의 절대 규칙 #1(수치는 LLM이 계산하지 않는다)과 같은 종류의 위험이다.
