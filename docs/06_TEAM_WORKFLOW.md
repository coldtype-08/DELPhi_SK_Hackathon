# 06. 팀 워크플로우 — 비개발자 3인 + Claude Code

> 원칙: **회의 최소, 문서 최대, 커밋 자주.** 우리는 코드를 직접 쓰는 게 아니라 Claude Code를 지휘한다.
> 지휘가 정확하려면 스펙(docs/)이 정확해야 하고, 충돌이 없으려면 오너십(CLAUDE.md)을 지켜야 한다.

## 1. Git — 이것만 지키면 안 꼬인다

- 브랜치: **main 하나만 쓴다.** (3인 + 폴더 오너십 분리면 충분. 브랜치 전략은 우리에게 오버엔지니어링)
- 세션 리듬: 시작 `git pull` → 작업 → 기능 단위 커밋 → 종료 `git push` + `docs/LOG.md` 한 줄.
- 커밋 메시지: `feat|fix|docs|style|chore: 한국어 설명 (console|field|backend|docs)`
- **충돌이 나면**: 당황하지 말고 Claude에게 "git 충돌 났어. 내 변경은 [설명]이야. 해결해줘." 그대로 맡긴다.
- 절대 금지: `git push --force`, 남의 오너십 폴더 대량 수정, .env(API 키) 커밋. `.gitignore`에 `.env`, `*.db`, `node_modules`, `data/cache` 포함 확인.
- GitHub 리모트는 백업이자 통합 지점. 하루 최소 1회 push 안 하면 아침 싱크에서 지적한다.

## 2. 매일의 사이클

| 시간 | 무엇을 | 비고 |
|---|---|---|
| 아침 (10분, 메신저) | ① 어제 완료 ② 오늘 목표(마스터플랜 칸) ③ 블로커 | 블로커는 폴더 오너가 당일 응답 |
| 저녁 작업 전 | `git pull` → CLAUDE.md 변경사항 확인 | 남이 스펙 바꿨을 수 있다 |
| 저녁 작업 후 | push + LOG 한 줄 + (스펙 바꿨으면) 아침 싱크에 공지 예약 | |
| 일요일 저녁 | **통합 체크포인트**: 화면 공유로 시나리오 처음부터 실행 | 마스터플랜의 Exit criteria 대조 |

## 2.5 스캐폴딩-소유 모델 (08/15 결정) — 누가 뼈대를 깔고, 누가 채우나

**뼈대는 건태가 미리 깔았고(8/15–20), 로직은 폴더 오너가 채운다.** "각자 빈 화면에서 시작"과 "붙이면 깨지는 통합 지옥"을 동시에 제거하기 위한 구조다.

| 구분 | 내용 | 담당 |
|---|---|---|
| 뼈대 (이미 있음) | DB 스키마·시드, fixtures 그대로 반환하는 stub API, 두 앱의 셸(토큰·레이아웃·라우트 껍데기), API 호출 유틸 | 건태 (아키텍트·통합자) |
| 속 (각자 채움) | 추출·집계·에이전트 로직(인혁), Field 수집 플로우·프롬프트(소정), Console 핵심 화면(건태) | 폴더 오너 |

- **작업 방식 = stub 교체.** 자기 영역의 stub·껍데기를 실제 구현으로 바꾸는 것이 곧 개발이다. 화면·API의 "모양"은 이미 있으므로 Claude Code에게 "이 stub을 docs/04 스펙대로 실제 구현으로 교체해줘"가 기본 프롬프트가 된다.
- **fixtures가 계약이다** (docs/04 §9). stub API가 이미 fixtures 모양을 반환하므로, 프론트와 백엔드는 서로를 기다리지 않는다. 응답 모양을 바꾸고 싶으면 docs/04 먼저.
- **공통 파일**(각 앱 `lib/`, 디자인 토큰, 다른 폴더의 stub)을 고칠 땐 `[cross]` 커밋 태그 + 오너 공유 — 기존 규칙 그대로.
- **건태의 저녁 루틴**: 매일 마지막에 `git pull` → 서버 3개 기동 → 화면이 뜨는지만 확인 (코드 리뷰 아님, "깨졌나" 확인). 깨졌으면 아침 싱크 안건.

## 3. Claude Code 운용 매뉴얼 (우리 팀의 진짜 개발 도구)

### 세션 시작 루틴
```
CLAUDE.md 읽고 시작해. 나는 [이름]이고 내 오너십은 [폴더]야.
오늘 작업: docs/00_MASTER_PLAN.md의 [날짜] 칸 중 "[작업명]".
관련 스펙: docs/[해당 문서]. 시작 전에 계획부터 보여줘.
```

### 잘 시키는 법 5가지
1. **문서 먼저 고치고 코드 시키기**: "docs/04에 이 엔드포인트 추가하고, 그 스펙대로 구현해줘." (문서-코드 불일치가 최악의 버그)
2. **레퍼런스 URL 던지기**: "https://magicui.design/docs/components/animated-beam 이걸 우리 토큰으로 이식해서 Screen 화면에 적용해줘."
3. **화면은 스크린샷으로 피드백**: 말로 설명하지 말고 캡처 붙여넣고 "여기 간격이 답답해, 여백 늘려줘."
4. **에러는 원문 통째로**: 터미널 에러를 그대로 복붙. "안 돼요"는 Claude도 못 고친다.
5. **의심하기**: Claude가 "완료했습니다" 해도 브라우저에서 직접 눌러보고 커밋. 특히 절대 규칙(수치 SQL 계산, evidence 필수)은 코드리뷰 요청: "방금 코드가 CLAUDE.md 절대 규칙을 어기는지 검토해줘."

### 프롬프트/스키마 작업 (소정 영역)의 특칙
- 프롬프트 파일 헤더에 버전·날짜·변경 이유 주석. 프롬프트 수정 = 커밋 필수 (재현성 추적의 대상이다).
- 같은 입력 3회 실행해 결과가 흔들리면: temperature 확인(0인지) → few-shot 예시 추가 → enum 정의를 더 좁게.

## 4. 의사결정 규칙

- **30분 룰**: 메신저 논쟁 30분 넘으면 해당 영역 오너가 결정하고 `docs/DECISIONS.md`에 한 줄 기록. (도메인 판단=건태, 판정 기준·UX 문구=소정, 데이터·기술 구조=인혁)
- cut line 변경(P0↔P1 이동)은 3인 합의 + 마스터플랜 수정 커밋으로만.
- **방법 비교(docs/00 §6)는 90분 상한.** 시한 내 결론이 없으면 기존 선택 유지 + 그 사실을 DECISIONS에 기록. 기록 없는 비교는 하지 않은 것으로 본다.
- "이거 넣으면 멋질 텐데"는 전부 `docs/PARKING_LOT.md`로. 9/1 freeze 이후 열람 금지.

## 4.5 기획서(제출본)와 docs의 관계 — 이게 꼬이면 심사에서 걸린다

제출한 **`예선기획서_DELPHI_0812_최종.docx`가 대외 약속**이고, `docs/`는 그것의 구현 스펙이다. 방향은 한쪽뿐이다.

| 상황 | 해야 할 일 |
|---|---|
| 기획서 내용을 docs가 아직 안 담았다 | docs를 고친다 (기획서가 기준) |
| 구현상 기획서와 다르게 갈 수밖에 없다 | **임의로 바꾸지 말고** DECISIONS에 "기획서 §X와 다름 + 이유 + 발표에서 설명할 문장"까지 기록. 예: docs/01 §8(Claude 단일 채택), docs/01 §3(REVIEWED 상태 미도입) |
| 기획서에 없는 걸 새로 만들고 싶다 | PARKING_LOT. 2주 안에 기획서 약속부터 다 지킨 뒤 |

**심사 질의 대비**: 기획서에 쓴 문장 중 "우리가 구현으로 증명해야 하는 것"은 docs/00 §1.5의 7개 + §5.1의 5개 리스크 대응이다. 리허설 때 각자 자기 영역 항목을 **화면으로 30초 안에 보여줄 수 있는지** 연습한다. 말로만 설명해야 하는 항목이 있으면 그건 미구현이다.

## 5. 보안·컴플라이언스 (해커톤이어도 지킨다)

- 실데이터·사내 문서·실명 절대 반입 금지. 합성 데이터 생성 시에도 실제 인물·기관명 사용 금지.
- API 키는 각자 로컬 .env. 메신저로 키 공유 금지 (1Password 등 사용).
- LLM 프롬프트에 "매출 예측", "HCP 설득 전략" 류 기능을 요청하지 않는다 — 기획서가 명시한 '하지 않을 것'이며, 심사 질의 때도 우리의 답변 기준이다.
