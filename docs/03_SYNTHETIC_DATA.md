# 03. 합성 데이터셋 설계·생성 가이드

> 목표: "실제 같은 비정형"이면서 **데모가 반드시 성공하도록 신호가 심어진** 코퍼스.
> 전부 가상 인물·기관·발언. 실제 HCP/환자/사내 데이터 절대 사용 금지 (기획서 5-3 §1).
> 담당: 인혁(생성) + 전원(리얼리티 검수). 위치: `backend/data/corpus/`, 생성기: `scripts/generate_corpus.py`.
> **08/14 개정**: 실물 원석 확인에 따라 영어 원석 + `HIGHLIGHT_DOC`(여러 HCP 묶음) 신설 + docx/pdf 포장 렌더 + 다국어 정책 반영 (DECISIONS 08/14).

## 1. 코퍼스 구성 — v2 (문서 90건 / 인사이트 단위 ≈ 165건, 08/21 회의 확장)

> **v1(63건/118단위) → v2 확장 이유 (08/21 회의)**: 가설이 2개만 나오는 코퍼스는 "시스템이 신호를 찾는다"가 아니라 "심어둔 두 개를 찾는다"로 보인다. 발굴 가설 2종(S7·S8)을 추가해 총 4개 가설이 임계값으로 자동 생성되게 하고, 노이즈·문체·기간도 함께 늘려 리얼리티를 높인다.

| 구분 | 문서 수 (v1→v2) | 언어 | 형식 |
|---|---|---|---|
| **하이라이트 묶음 (HIGHLIGHT_DOC)** | 12→**16** | EN | 실물 원석 양식 재현 (§3.5). 문서당 HCP 블록 4~6개(블록 합계 ≈ 80) — **추출이 블록 단위로 interaction 분리** (docs/02 §1) |
| **학회 참관 보고서 (CONGRESS_REPORT)** | 3→**5** | EN | **PDF 원석** (§3.5). 세션·KOL 대화 서술 + 포스터 세션 대화 장면 — 블록 분리 대상 (문서당 3~4 대화) |
| 면담 기록 (MEETING_NOTE) | 25→**34** | EN | 자유서술, 1문서=1면담. 문체 다양화 필수 (§3) |
| 전화 메모 (CALL_NOTE) | 10→**14** | EN | 짧은 개조식 |
| 이메일 요약 (EMAIL_SUMMARY) | 10→**14** | EN | 이메일체 |
| 음성 전사 (VOICE_TRANSCRIPT) | 3→**7** | KO | 구어체 대화록 — **Field 데모 리허설용** (§6) |

- **신호 분포의 "건"은 인사이트 단위(interaction) 기준**이다 (08/14) — 하이라이트형 1개 문서가 여러 단위를 담는다. 집계·SQL도 이 단위로 계산되므로 docs/04의 예시 수치(반복 14건 등)와 일치한다.
- 기간 분포: **2025-03 ~ 2026-07 (17개월)** — 추이 곡선이 길어지고, S7(PGTC)은 후반부에 밀도가 올라가는 모양으로 배치(외부 학계 흐름과 현장 질문이 함께 늘어나는 서사).
- 작성자(가상 MSL) **6인** × HCP **30인**(가명 HCP-001~030) × 4권역(`NORTHEAST` `SOUTH` `MIDWEST` `WEST` — docs/02 §1과 일치) × 3 세팅 분산. 다주제 HCP(신호 2종 이상 언급)를 v1보다 늘린다 — 전문가 관여 화면이 참아진다.

### 1.5 언어 정책 (08/14 확정)

- **원석(하이라이트·면담·콜·이메일) = 영어.** 실데이터(약 300건 docx — "쓰지 못하던 원석")가 전부 영어이기 때문. 해커톤에는 반입하지 않고 파일럿 검증 카드로만 쓴다.
- **Field 신규 수집·음성 전사 = 한국어** (ko-KR Web Speech).
- **데모에서 두 언어를 모두 시연한다**: 시나리오 ②에서 영문 원석이 구조화되고 → ③에서 한국어 면담이 수집되어 → **같은 canonical 코드로 같은 집계에 합산**되는 순간(예: 영문 S1 + 한국어 음성 S1 → `PEDIATRIC_TRANSITION` +1)이 다국어 전략의 증명이다. 원칙(스키마 언어중립·verbatim 원언어·정규화 계층이 언어 흡수)은 docs/02 §3.
- 화면 라벨과 `summary_ko`는 항상 한국어 (UI는 한국어, 원문은 원언어 그대로).

## 2. 심어야 하는 신호 (Planted Signals) — 데모의 각본

**가설 4개의 역할 분담 (08/21 회의 — 발표 서사)**: ① S1(청소년)은 회사가 **실제로 임상·연령 확대를 진행 중**인 주제(공개 CT.gov 등록 기준)라 "정답을 아는 문제" — 시스템이 현장 대화만으로 같은 신호를 재발견하는 **검증 축**. ② S7(PGTC)·S8(LGS)은 **발굴 축** — 관객이 결말을 모르는 상태로 임계 도달 → 가설 자동 생성 → Board까지 라이브로 본다(S7이 완주 대표). ③ S6(노인)은 In-label **대비 축**. "우리 회사가 수년에 걸쳐 내린 전략 방향을, 이 시스템은 면담 데이터만으로 재구성한다"가 발표의 한 문장이다.

| ID | 내용 | 분포 (인사이트 단위) | 데모에서의 역할 |
|---|---|---|---|
| **S1 검증 가설 (Development)** | 청소년(12–17세) 약물난치성 초점발작 — 성인 허가라 쓸 수 없어 18세까지 대기하는 치료 공백 | **14건 / 독립 HCP 9인 / 3권역** | HYP-001. 반복수·출처수·지역분포가 SQL로 잡힌다. **회사가 실제 진행 중인 확대와 일치 = 성능 검증 서사.** 허가 범위 밖이라 상업 액션 차단 시연의 축 겸용 |
| **S2 안전성 분기** | 어지러움·졸림·발진·피로 등 이상사례 시사 발언 | **7건** (용어 5종 이상 다양화, S1·S7 단위에 섞기) | Field/Sense에서 자동 분기 시연. 일반 집계에 안 섞이는 것 증명. PV 화면의 용어 집계가 참아진다 |
| **S3 스키마 공백** | "뇌졸중 후 뇌전증(post-stroke epilepsy)" 환자군 언급 — **v0.1 enum에 없음** | 6건 / HCP 4인 | unmapped 반복 → SCP 자동 제안 → v0.2 승격 시연 (구조 루프) |
| **S4 자료 요청 반복** | 청소년 용량·안전성 + **PGTC 관련 문헌** + 노인 DDI 자료 요청 | **12건** | INFO_REQUEST 집계, 미해결 질문 → Field 체크리스트 (실행 루프 연료) |
| **S5 긍정 신호** | DRE(약물난치성) 성인 환자 발작 감소 경험 | **9건** | 대시보드에 긍정 신호도 있음을 보여주는 균형추 |
| **S6 In-label 대비 가설** | 노인(65+) 병용약물 상호작용·적정 부담 → 자료·교육으로 해소 | 10건 / 독립 HCP 6인 | HYP-002(In-label). Development와 **나란히** 표시해 두 종류의 분리를 증명 |

| **S8 발굴 가설 ② (Development, 08/21 신설)** | 레녹스-가스토 증후군(LGS) — 드롭발작·다발작형에서 기존 약물 한계 반복 언급 | **7건 / 독립 HCP 5인 / 3권역** | HYP-004 — 두 번째 발굴. 외부 근거가 얇으면 `NOT_BOARD_READY(NO_EXTERNAL_EVIDENCE)`로 남는 것 자체가 시연 포인트(근거 없으면 순위를 안 매긴다) — §7 스냅샷 확인 후 각본 확정 |
| 노이즈 | 학회 일정, 일반 근황, 경쟁 치료 일반론, 병원 행정 얘기, 보험 커버리지 일반 문의 | 나머지 전부 (인사이트 단위의 절반가량) | 리얼리티. 추출기가 OTHER/무시 처리하는 것 증명 |

**임계값 검산 (docs/01 §3 기본값: 반복 ≥5 ∧ 독립 HCP ≥3, UNMET_NEED·TREATMENT_BARRIER 한정)**: S1·S6·S7·S8 넷만 통과 → HYP-001~004 정확히 4개 생성. S3는 enum 미존재라 unmapped→SCP, S4(INFO_REQUEST)·S5(POSITIVE_OUTCOME)는 대상 밖.

**규칙: S1~S8 문장은 ground truth에 정확히 기록하고, 신호 문장도 문서마다 표현을 다르게 쓴다** — 동의어 정규화가 일할 거리를 만든다. 영어 원석은 영어 변형("elderly" / "older adults" / "geriatric patients"; PGTC는 "generalized tonic-clonic" / "GTC" / "convulsive generalized"), 한국어 전사는 한국어 변형("고령 환자", "어르신들"; "전신발작", "대발작"). **두 언어가 같은 canonical로 수렴하는 쌍을 최소 S1·S6·S7에 하나씩** 배치한다 (§1.5의 합산 시연용).

## 3. 리얼리티 규칙 (심사위원이 믿게 만드는 디테일)

1. 문체 혼합: 원석(영어) ① 서술형 보고체 ② ➤ 화살표 개조식(하이라이트형 기본) ③ 이메일체 / 음성 전사(한국어) ④ 구어 전사체. 같은 작성자는 같은 버릇 유지.
2. 오타·비문 5% 의도적 포함. 영어 원석: 오탈자·약어 불일치(cenobamate/XCOPRI/CNB 혼용, 기관명 축약). 한국어 전사: 구어 잉여어·영한 혼용("titration 스케줄이…", XCOPRI/엑스코프리/세노바메이트 혼용).
3. 길이 편차: 개별 문서 300~1,800자, 하이라이트 블록 80~400자. 신호가 없는 문단·블록이 절반 이상.
4. 개인정보 마스킹 데모용 3건: **영어 문서 2건**(가상 실명·미국식 전화 패턴 "Dr. ___, (555) 123-…") + **한국어 음성 1건**("김OO 선생님, 010-XXXX-…") → 수집·적재 단계 마스킹이 두 언어 모두에서 작동함을 연출. `masked_spans` 정답지를 manifest에 미리 계산.
5. 의학적 사실관계는 공개 라벨 수준만 사용, 효능 과장 표현 금지 (Critic 차단 시연용 문장 2건은 예외로 의도 삽입: **"safe for adolescents too"**(허가 범위 벗어난 단정), "works for every patient"(과일반화) → Critic이 잡는 장면).
6. **Development 신호(S1·S7·S8)는 절대 "처방하자"로 쓰지 않는다** — 어디까지나 "쓸 수 없어서 생기는 공백"의 기록이다. 오프라벨 사용을 권유·시사하는 문장은 어느 언어로도 코퍼스에 넣지 않는다. (S7 예: "전신발작 환자에게도 써보고 있다" 금지 → "전신발작 환자에겐 선택지가 없어 답답하다" 형태만.)

### 3.5 하이라이트형 양식 명세 (실물 구조 — 08/14 확보)

> 실물의 가림 캡쳐에서 **구조만** 추출한 명세다. 캡쳐 자체는 폐기했고 레포에 넣지 않는다. 내용·인물·기관은 전부 가상으로 채운다.

```
┌ 1행: 문서 제목 "[조직명] Medical Affairs Highlights"        우상단: 날짜 (파란색 강조)
├ 2행: "From:" + 공동 작성자(가상 MSL 이름들) 나열
├ 회색 배경 밴드(표 셀): 섹션 타이틀 "Field Medical Insights" (가운데 정렬, 볼드)
└ HCP 블록 반복 (4~6개):
   ├ 볼드 헤딩: [First Last], MD, [기관 풀네임], [City], [ST] ([역할코드 RSM|AR])
   │            └ 레지던트면 "PGY2/PGY3 resident" 등 직급 병기
   └ ➤ 화살표 불릿 1~4개: 영어 자유서술, 직접 인용("He stated, '…'") 혼재
       주제 풀: 용량 적정 습관 · 병용약 조정 · 보험/접근성 · 자료 문의(임신 데이터 등)
               · 적응증 확대 일정 질문 · 효능 관찰 소감 · (노이즈) 학회·근황
```

- docx 렌더 템플릿: `scripts/templates/highlight_doc.docx` — 제목행·회색 밴드·볼드 헤딩·➤ 불릿 스타일을 재현하고 python-docx로 채운다.
- **학회 보고서(PDF) 양식**: 표제(가상 학회명·기간·작성 MSL) → 세션별 서술 단락 → **"Poster Session" 단락**(포스터 앞에서 나눈 대화를 서술 — **포스터·논문 원본은 반입하지 않는다**: 저작권 + 그 내용물은 Screen의 외부 공개 근거 영역) → Follow-up 목록. 렌더는 reportlab 단순 서식. 3건 중 1건 이상에 S1(청소년 공백 질문)·S4(자료 요청) 신호를 포스터 대화 장면으로 배치.
- 검수 통과 기준 "우리 회사 문서 같다"에 **양식 재현도 포함**.

## 4. 파일 포맷

```
backend/data/corpus/
├── DOC-20251201-001.txt        # 정본 원문 (마스킹 후) — 모든 evidence 오프셋의 기준
├── DOC-20251201-001.docx       # 같은 원문의 "포장" 렌더 (하이라이트형 12건 전부 + 면담 8건)
├── DOC-20260315-007.pdf        # 학회 참관 보고서 3건 (CONGRESS_REPORT)
├── manifest.jsonl              # 한 줄 = 한 인사이트 단위(interaction): docs/02 §1 필드 전부
│                               #   + {file, source_format, language, block_index, doc_char_start/end}
└── ground_truth.jsonl          # 한 줄 = 한 정답 claim: {file, interaction_ref, signal_id, verbatim_quote,
                                #   char_start, char_end(문서 전문 기준), signal_type, patient_segment, barrier_type}
```

- **정본은 항상 `.txt`** — evidence pointer(문자 오프셋)의 기준은 문서 전문 텍스트다 (절대 규칙 #2). docx/pdf는 같은 원문의 포장이며, **렌더 후 텍스트를 재추출해 정본과 일치하는지 자가검증**한다 (우리가 만든 파일이라 파싱이 결정론적 — 실세계 지저분한 PDF 리스크 없음).
- `ground_truth.jsonl`은 **채점용**: 추출 파이프라인의 재현율/수용률 측정(9/2 재현성 테스트)과 리뷰 데모 준비에 쓴다. 서비스 로직은 이 파일을 절대 읽지 않는다.
- 수용률(reviewer acceptance) 정의는 기존과 동일: `승인 claim ÷ 검토 완료(승인+반려) claim` (docs/02 §5.5). 기획서 §6-2의 90% 목표는 파일럿 검증 대상(docs/00 §1), 해커톤에서는 참고 수치만.

## 5. 생성 방법 (`scripts/generate_corpus.py`)

1. **각본 먼저**: 스크립트 상단에 §2 표를 파이썬 dict로 고정 — 문서×블록 단위로 어떤 신호·어떤 표현 변형(언어 포함)이 들어가는지 결정론적으로 배정. 하이라이트형은 블록별 각본을 갖는다.
   - **신호 문장(verbatim)은 스크립트가 소유한다.** LLM은 주변 텍스트만 쓰고 신호 문장은 그대로 심는다 → 데모 각본(S1의 14건/9인/3권역)이 LLM 출력 품질에 흔들리지 않는다.
   - **대명사 규칙**: 영어 원석에서 HCP를 `he/she`로 지칭하지 않는다(역할 명사·they·무주어). 가명 HCP의 성별을 이름으로 추정하지 않고, 각본 문장과 HCP 명부 간 성별 불일치 버그를 구조적으로 없애기 위함. 검증기가 강제한다.
2. **블록 본문(prose) 확보 — 두 경로. 어느 쪽이든 산출물은 동일하다.**
   - (a) **세션 내 작성 (기본)**: Claude Code 세션에서 직접 써서 `scripts/corpus_bodies/*.json`에 저장 (`{"H01": {"1": "본문", …}}`). API 키가 필요 없고, 랜덤성이 없어 재현성이 완전하다. 이 파일들은 **커밋 대상** — 코퍼스 재생성의 입력이자 재현성의 근거다.
   - (b) **Claude API 생성 (대안)**: `.env`에 `ANTHROPIC_API_KEY`가 있으면 본문이 없는 블록만 API로 채운다. temperature 0.8.
   - 스크립트는 (a)를 우선 읽고, 준비본이 규칙을 위반하면 **조용히 API로 넘어가지 않고 즉시 실패**한다(어느 파일 어느 블록인지 표시).
3. **자가 검증**: 신호 문장 정확히 1회 포함 + 블록 구조(불릿·문단 형태) + 성별 대명사 금지 + 길이 범위 → verbatim 위치(문서 전문 기준 char offset) 계산해 ground_truth 기록. 하이라이트형·학회형은 블록 경계(doc_char_start/end)도 함께 기록.
4. **포장 렌더**: 하이라이트형 12건 전부 → `.docx`(§3.5 템플릿), 면담 기록 8건 → `.docx`, 학회 보고서 3건 → `.pdf`(§3.5 양식). 렌더 → 텍스트 재추출 → 정본 일치 자가검증 통과해야 산출.
5. `manifest.jsonl` 생성 → `scripts/seed_db.py`가 documents(문서 전문) + interactions(단위) 분리 적재.
6. **사람 검수(8/15–18)**: 3인이 문서 ~20건씩(하이라이트형은 블록 단위로 훑기) 읽고 어색한 것 flag → 재생성. 통과 기준: "우리 회사 문서 같다" (내용 + 양식).
7. **Contract 부트스트랩 연계 (08/14)**: 검수 통과 샘플 10~20건을 Claude에 주고 "이 데이터에서 뽑아야 할 필드·허용값"을 초안으로 제안받아 v0.1 초안과 대조·반영 (8/18–20, 90분 상한 — docs/00 §6 준용). 채택·기각을 DECISIONS에 기록해 "시드 스키마도 AI 초안 + 사람 확정"을 사실로 만든다.

## 6. 음성 전사 7건 (Field 데모용 — 한국어, v2에서 3→7건)

- 추가 4건(v2): S7 한국어 변형("전신발작 환자에겐 선택지가 없다") 2건 — **다국어 수렴 시연을 발굴 가설에서도** 가능하게 함 — + S6 변형 1건 + 순수 노이즈 1건(신호 없는 면담도 있다는 리얼리티).
