01

큰 개발 흐름 — 기존 계획 위에 배포 레일 한 줄

위 줄(네이비)은 docs/00 마스터플랜 그대로. 아래 줄(오렌지)이 이 가이드가 추가하는 전부다.

흐름을 지배하는 세 가지 원칙 (docs/00에서 그대로)

  • 문서 → 코드 순서. 새 기능은 docs를 먼저 고치고 Claude Code에게 "이 스펙대로"라고 시킨다. 스펙이 정확할수록 바이브 코딩 결과물이 정확하다.
  • 루프 완결 > 기능 수. 대표 가설 HYP-001 한 건이 ①~⑥ 시나리오를 끊김 없이 관통하는 것만이 완료 기준이다. 망설여지면 cut line 드랍 순서를 기계적으로 적용.
  • 라이브 발표의 정본은 로컬. 클라우드 배포는 심사위원의 "자유 접속"용이고, 무대 위 시연은 지금 계획대로 노트북 로컬 + DEMO_OFFLINE=1 캐시로 돌린다. 배포가 실패해도 발표는 무사하다.
거버넌스 — 08/14 처리 완료

클라우드 배포는 08/14 중앙 결정(팀 배정 전 팀장 결정 체제)으로 P2 → P0 승격이 확정되었고, docs/00(일정)·docs/07(배포 문서 신설)·DECISIONS에 반영 완료. 팀원은 정독 시 docs/07을 함께 읽으면 된다. 같은 날 코퍼스 방향(영문 원석 + 하이라이트형 + HCP 블록 분리 + docx/pdf 포장)도 확정되어 docs/02·03·04가 개정되었다.

02

브랜치 흐름 — main 하나를 지키고, 안전장치 둘만 얹는다

"main 단일 + 폴더 오너십"은 08/11에 이미 기록된 팀 결정이고, 비개발자 3인에겐 여전히 정답이다. 배포가 붙으면 딱 하나가 달라진다: push가 곧 화면이 된다.

그대로 유지 이미 있는 규칙
  • 세션 리듬: 시작 git pull → 작업 → 기능 단위 커밋 → 종료 push + LOG 한 줄
  • 커밋 메시지: feat|fix|docs: 한국어 설명 (영역)
  • 오너십 밖 수정은 [cross] 태그 + 즉시 공유
  • 금지: --force push, .env·*.db 커밋
  • 충돌 나면 Claude에게 그대로 맡긴다 — "충돌 났어, 내 변경은 ○○야, 해결해줘"
새로 추가 배포 시대의 두 장치
  • ① 마일스톤 태그. 체크포인트 통과 순간마다 Claude에게 "지금 커밋에 w1-exit 태그 달아줘". 되는 상태로 언제든 돌아갈 수 있는 북마크다. 마지막은 demo-final.
  • ② push 승격 규칙. 9/3 심사 URL 공유 후엔 "로컬에서 시나리오 한 바퀴 돈 커밋"만 push. 그래도 깨지면 브랜치로 고민하지 말고 Railway에서 직전 배포로 롤백.

feature 브랜치·PR을 쓰지 않는 이유도 기록해 두자: 리뷰어가 없는 3인 팀에서 PR은 의식(儀式)이지 안전망이 아니다. 우리의 실제 안전망은 폴더 오너십(충돌 방지) + 태그(복구 지점) + 롤백(배포 복구) 세 개다.

03

배포 — Vercel이 아니라 Railway 하나로 가는 이유

질문 주신 Vercel은 방향 자체는 맞다. 다만 우리 스택의 한 조각이 Vercel에 올라가지 않는다.

Vercel은 Next.js 프론트 2개(console·field)는 완벽하게 받아주지만, 백엔드가 문제다. 우리 백엔드는 FastAPI + SQLite 파일(backend/data/delphi.db)인데, Vercel은 서버리스 방식이라 요청이 끝나면 파일이 사라지는 임시 디스크 위에서 돈다. 즉 DB가 못 산다. 백엔드는 디스크가 붙는 상시 서버가 필요하고, 그런 서버를 주는 플랫폼(Railway)은 Next.js도 같이 돌릴 수 있다. 그러면 답은 자연스럽다: 플랫폼 두 개를 배우지 말고, 셋 다 올라가는 하나만 배우자.

셋업은 4번에 나눠서, 한 번에 30–60분

날짜담당무엇을

8/24 배포 데이 — Claude Code에 붙여넣을 프롬프트

CLAUDE.md 읽고 시작해. 오늘 작업: Railway 배포 세팅 (docs/07 참고).
목표: backend / apps/console / apps/field 3개 서비스를 Railway 한 프로젝트(싱가포르 리전)에 올린다.
- backend: uvicorn 시작 명령, /data 볼륨에 SQLite·캐시, 환경변수 ANTHROPIC_API_KEY · ALLOWED_ORIGINS · DEMO_OFFLINE · RESET_TOKEN
- console·field: NEXT_PUBLIC_API_BASE_URL로 backend 공개 URL 연결, backend CORS에 두 프론트 도메인 허용
- 완료 기준: 배포된 Console에서 문서 목록이 뜨고, 내 폰에서 Field URL이 열린다
필요한 설정 파일은 네가 만들고, 내가 Railway 대시보드에서 클릭해야 하는 건 순서대로 하나씩 알려줘.

운영 원칙 세 가지

  • 심사위원은 언제 와도 "데모 시작 상태"를 본다. 여러 명이 눌러보면 승인 상태가 뒤섞이므로, 리셋 엔드포인트로 매일 아침(또는 자동으로 자정마다) 시드 상태로 되돌린다. 이미 만들 reset_demo.sh의 재활용이라 신규 개발이 거의 없다.
  • 비용: 해커톤 전체 ≈ 1~2만 원. Hobby 플랜 $5/월 + 소형 서비스 3개 사용량. 무료 체험 크레딧으로 시작하고 늦어도 9/1 전에 전환(무료 상태로 심사 맞으면 콜드스타트로 첫 화면이 30초 걸릴 수 있다). 끝나면 바로 해지.
  • 요건이 어떻게 확정되든 이 설계는 유효하다. "상시 접속"이면 그대로 쓰고, "발표 당일만"으로 확정되면 같은 배포를 유지한 채 URL 공유만 당일에 하면 된다. 손해 보는 시나리오가 없다.

대안 참고: 프론트 2개만 Vercel + 백엔드만 Railway로 나누는 조합도 기술적으로는 가능하지만, 대시보드·환경변수·도메인 관리 지점이 두 배가 된다. 비개발자 3인 팀에는 "배울 플랫폼 하나"가 더 큰 가치다.

04

맥스튜디오 — 개발서버로 쓰지 않는 게 맞다

좋은 장비지만, 이 프로젝트의 아키텍처가 공유 개발 서버를 필요 없게 설계돼 있다.

✕

공유 개발 서버 — 필요가 없다. DB가 SQLite 파일이라 각자 노트북에서 seed_db.py로 자기 DB를 만들어 풀스택을 돌리는 게 설계 의도다. 중앙 dev 서버를 두면 오히려 서로의 테스트 데이터를 밟는다. LLM도 Claude API(클라우드)라 로컬 연산력이 쓰일 곳이 없다.

✕

심사위원용 호스팅 (Cloudflare Tunnel 등) — 가능은 하지만, 집 공유기 재부팅·정전·ISP 순단이 심사 기간 내내 단일 장애점이 된다. 서버 상태를 지켜보는 일 자체가 비개발자에게 새 업무다. 유료 OK라고 하셨으니 월 $5 클라우드가 모든 면에서 우위.

○

발표장 백업 머신 — 이건 좋다. 발표 노트북과 동일한 로컬 스택 + DB 스냅샷 + 리허설 녹화 영상을 넣어 두면, 인혁 담당의 "장비·환경 백업 대기"(9/4) 그 자체가 된다. 합성 코퍼스 대량 생성 같은 배치 작업용으로도 소소하게 유용.

정리하면: 맥스튜디오에 시간을 쓰지 말고, 그 시간을 8/24 첫 배포에 쓰자.

05

"비정형이 처리되는 부분"은 이렇게 보여준다

걱정하신 지점이 사실은 우리 제품의 최대 시각화 자산이다. 절대 규칙 #2가 모든 추출값에 원문 문자 위치를 강제해 놨기 때문에, 그릴 재료가 이미 데이터에 있다.

보여줄 것은 두 층이다. 결과의 시각화(구조화된 값이 원문 어디서 왔는지)는 이미 P0 계획에 있고, 빠져 있던 과정의 시각화(처리되는 순간)는 "추출 리플레이" 연출 하나로 채운다.

네 가지 장치 — 셋은 이미 계획에 있다

  • P0 · 이미 계획 원문↔카드 양방향 하이라이트 (8/22, 건태). 카드 클릭 → 원문 스크롤+형광펜, 원문 클릭 → 카드 포커스. 위 그림의 뼈대이자 심사 증명 화면.
  • 신규 제안 추출 리플레이 연출. 백엔드 추출은 사전에 끝내 두고, 화면은 저장된 claim들을 0.4초 간격으로 순차 등장시키며 형광펜이 좌→우로 그어지는 모션을 건다(framer-motion stagger + 이미 있는 문자 오프셋). LLM 스트리밍이 아니라 저장 결과의 재생이라 데모에서 절대 실패하지 않는다. 라벨은 정직하게 "추출 완료 · 결과 재생" — 심사위원이 물어도 떳떳하다. 자리: 8/26 "원문 추적 UX" 날 또는 9/1 폴리시 날, 반나절.
  • 신규 제안 파이프라인 상태 보드. 대시보드 홈(8/24)에 문서 63건의 RAW → CANDIDATE → APPROVED 단계별 카운트 스트립 한 줄. Field에서 승인하는 순간 숫자가 +1 카운트업되는 게 "루프가 닫히는" 순간의 시각화다. 숫자는 물론 SQL.
  • P1 · 이미 계획 Screen 에이전트 animated beam + Board 심의 스트리밍. 4개 에이전트가 근거를 물어오는 장면과 이사회 회의록 — 후반부 "처리 시각화"는 이 둘이 담당하며 P1 최우선 순위 그대로 지킨다.
연출에도 절대 규칙

등장하는 모든 숫자는 SQL 집계값(#1), 카드엔 5단계 구분 뱃지(#8), "AI가 지금 생각 중" 같은 과장 문구 대신 사실 그대로의 라벨. 화려함은 모션에서 얻고, 문구는 감사(audit) 가능해야 한다 — 이게 심사에서 "일반 요약 도구와 다른 이유"를 지키는 방식이다.
