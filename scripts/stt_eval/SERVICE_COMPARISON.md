# STT 후보 3종 비교 — Soniox · Deepgram · Gladia

> 8/24 실기 테스트(DECISIONS 08/21 [소정])의 사전 조사. **작성: 인혁 / 최종 갱신: 08/22**
> 랩으로 직접 돌려보는 방법은 `apps/stt-lab/README.md`, 대본·채점 기준은 `TEST_SCRIPTS.md`.

## 0. 표기 규칙 — 이 문서에서 제일 중요한 부분

| 표기 | 뜻 |
|---|---|
| **[확인]** | 벤더의 **정본**에서 읽었다 — SDK 소스, OpenAPI, AsyncAPI 스펙 |
| **[추정]** | 근거가 약하다. 공개 문서를 열지 못해 SDK·샘플에서 유추했다 |
| **[실측]** | 스펙만으로는 답이 없다. **8/24에 돌려봐야 안다** |

**마케팅 페이지 문구는 근거로 쓰지 않았다.** 실제로 어긋난 사례가 있다 — Gladia는 소개 페이지와
SDK 산문에 실시간 화자분리가 있다고 되어 있으나, 요청 OpenAPI와 응답 AsyncAPI 어디에도 해당 필드가 없다.
그래서 "된다/안 된다"를 단정하지 않고 랩에서 실제로 보내보게 만들었다(§4).

사내 프록시에서 세 벤더의 공개 문서 사이트가 모두 막혀 있다(403). 그래서 GitHub에 올라온
SDK 소스와 스펙 파일을 직접 읽었다 — `deepgram/deepgram-api-specs`, `soniox/soniox-python`,
`gladiaio/docs`. 이것이 문서보다 오히려 정확하다(구현이 읽는 실물이므로).

## 1. 우리가 정한 컷오프 — 하나라도 못 하면 탈락

DECISIONS 08/22 [인혁]에서 확정한 4개다. 순위는 그다음, **지연이 낮은 쪽**이 유리하다.

1. **실시간 스트리밍** — 브라우저에서 말하는 중에 텍스트가 나와야 한다
2. **실시간 화자분리** — MSL과 의사를 갈라야 한다
3. **keyword boosting** — 도메인 용어를 미리 먹여야 한다
4. **언어 케이스 정확도** — 한국인 의사(한국어 + 영어 용어 혼용)

> **2번(화자분리)을 필수로 둔 이유**: `verbatim_quote`는 **HCP의 발언**이어야 하고,
> `solicitation`(발언 경위 — MSL이 물어서 나온 말인가 의사가 먼저 꺼낸 말인가, `docs/02` §2)
> 판정 자체가 화자를 전제한다. 화자를 모르면 MSL의 질문이 의사의 신호로 집계될 수 있다.
>
> **3번(부스팅)을 필수로 둔 이유**: 전사 텍스트가 `interactions.raw_text`가 되고 모든 evidence
> 오프셋의 기준(`docs/02` §1)이라, "전신 강직-간대발작"을 놓치면 그 아래 파이프라인 전체가 무의미하다.

## 3. 서비스별로 알아야 할 것

### Deepgram — 의료 특화와 한국어를 동시에 못 한다 / 실시간 화자분리는 구세대 모델뿐

**화자분리 [확인+실측] (08/22)**: `diarize_model`을 주면 그것만으로 화자분리가 켜진다(`diarize=true` 불필요 — 공식 JS SDK 주석).
단 **스트리밍에서 지원되는 모델은 v1이 전부**이고 신형 v2는 배치 전용이다(스트리밍에 v2 → validation error).
실측에서도 한국어 짧은 턴 대화(TTS 2종 + 직접 발화)에서 화자 경계가 불안정했고 화자 수를 과분리(0/1/2)했다.
설정 오류가 아니라 서비스의 실시간 화자분리 수준 그 자체다 — **Soniox와 같은 소리로 비교하는 것이 남은 판정**이다.

이 한 줄이 핵심이다. `nova-3-medical`은 의료 용어에 특화됐지만 **한국어를 지원하지 않는다**.
`nova-3`은 한국어를 하지만 의료 특화가 없다. 즉 **한국인 의사를 대상으로 하면 Deepgram의
가장 큰 강점이 사라진다.** 우리 대본 3종(P1·D1·T1)이 전부 한국어이므로 `nova-3`으로 돌려야 한다.

- `diarize` 파라미터는 **Deprecated**다. `diarize_model=v1`을 쓴다 (v2는 스트리밍 미지원).
  **둘을 같이 보내면 요청이 거부된다**(공식 diarization 문서). 화자분리는 "All available languages" —
  한국어도 공식 지원이므로, 관찰된 낮은 품질은 미지원이 아니라 실시간 v1 모델의 실력이다.
  문서는 신규 연동에 `diarize_model=latest`를 권장하지만 **우리는 `v1` 고정** — latest는 스트리밍 v2가
  출시되는 순간 동작이 소리 없이 바뀌어 8/24 판정과 9/4 시연 사이의 재현성이 깨진다.
  실제로 어떤 버전이 돌았는지는 응답 metadata `diarize_info.arch`로 확인할 수 있다.
- `keyterm`은 파라미터를 반복해서 여러 개 준다. 한도 500 tokens, 문서 권고는 "중요한 20~50개".
  **가중치를 붙일 수 없다** — 붙이면 조용히 무시되므로 "먹었는지" 확인이 안 된다.
- 브라우저는 커스텀 헤더를 못 쓰므로 `new WebSocket(url, ["token", key])`로 인증한다.
- **비용**: 신규 $200 크레딧이 있어 해커톤 기간 실측 부담이 가장 낮다.
- **켜는 기능 — Numerals** (`numerals=true`): 숫자를 항상 숫자 표기로. **한국어 공식 지원**이고
  치명 토큰(`17세`·`18세`·전화번호)과 `masked_spans` 정규식이 숫자 표기를 전제한다 (08/22 검토).
- **켜지 않는 기능 — Redaction** (`redact`): ① 마스킹은 **우리 파이프라인의 시연 포인트**다 — 벤더가
  전화번호를 먼저 지우면 `masked_spans` 장면이 사라지고 T1 채점도 무의미해진다. ② 어차피 한국어는 못 쓴다 —
  스트리밍 숫자 삭제 12개 언어에 ko 없음, 개체(이름·주소·PHI) 삭제는 영어 전용. **서버측 마스킹 설계의 추가 근거** (08/22 검토).
- **켜지 않는 기능 — Dictation** (`dictation=true`): 구술용 기능(말한 "comma"를 부호로 변환), 영어 전용.
  우리는 자연 대화 전사라 해당 없고, 의료 영어에서 "period"(월경)를 마침표로 바꿔버릴 위험까지 있다.
  문장부호는 `punctuate`+`smart_format`으로 이미 처리 중 (08/22 검토).

### Soniox — 스펙상 컷오프 4개를 유일하게 다 만족한다

- `enable_speaker_diarization`·`language_hints`·`context.terms`·임시 API 키 전부 SDK 필드로 확인했다.
- `context`는 용어 목록(`terms`)과 도메인(`general.domain`)을 함께 줄 수 있어, 부스팅이
  세 서비스 중 가장 표현력이 크다.
- **리전에 일본이 있다** — 한국에서 왕복 지연이 유리할 가능성이 높다. 다만 [실측] 필요.
- ~~약점: WS 경로·audio_format이 추정값~~ → **08/22 해소.** `soniox-python` SDK 소스에서 직접 확인했다 —
  `src/soniox/client.py:39`에 `wss://stt-rt.soniox.com/transcribe-websocket`, 타입 정의에 `pcm_s16le`.
  이제 세 서비스 주소가 전부 [확인]이다.

### Gladia — 화자분리 미지원 실측 확정 (08/22): `diarization` 전송 → **400 Invalid parameter(s)**. 컷오프 2번(실시간 화자분리)에서 탈락. 이하는 기록용

정본 두 곳을 다 봤다. 요청 쪽 OpenAPI(`POST /v2/live`)에 화자분리 파라미터가 없고,
응답 쪽 AsyncAPI의 `Utterance` 객체에 `speaker` 필드가 없다. 반면 산문 문서와 SDK 응답 타입에는
`speaker`가 나온다. **어느 쪽이 맞는지 스펙만으로는 결론이 안 난다.**

- `code_switching`은 **발화(utterance) 단위** 언어 자동 감지다. `languages`를 하나만 주면 무시된다.
  즉 "한 문장 안에서 한국어와 영어가 섞이는" 우리 케이스(T1)를 겨냥한 기능이 아니다.
- `custom_vocabulary`에 **intensity를 줄 수 있다** — 세 서비스 중 부스팅 강도를 조절할 수 있는 유일한 곳.
- 키가 클라이언트에 남지 않는 설계(2단계 접속)로 **보안 구조가 가장 깔끔하다.**
- **리전이 us-west·eu-west뿐이다** — 아시아가 없어 한국에서 지연이 불리할 가능성이 높다.

## 4. 랩이 실측으로 답을 내주는 것

스펙으로 답이 안 나는 항목은 랩이 실제로 시험한다.

| 항목 | 어떻게 판정하나 |
|---|---|
| 화자 라벨이 실제로 오나 | 세그먼트에 화자 번호가 붙는지 화면에서 바로 보인다 |
| 부스팅이 먹었나 | 부스팅 on/off로 한 번씩 돌려 **핵심 토큰 히트 수를 비교** (특히 `전신 강직-간대발작`·`titration`) |
| 지연 | 「첫 응답 ms」 — **3종 동시 실행**으로 같은 순간의 같은 소리를 받았을 때만 비교가 유효하다 |
| 한↔영 혼용 정확도 | T1 대본의 `DDI`·`titration`·`lamotrigine` 히트 여부 |

## 6. 탈락한 후보들 — 왜 3종으로 좁혔는지

컷오프 4개를 적용하면 아래는 검토 단계에서 빠진다. 되짚을 일이 없도록 사유를 남긴다.

| 후보 | 탈락 사유 |
|---|---|
| **Deepgram Flux** (`/v2/listen`, 턴 기반 신형) | **응답 스펙에 화자 필드가 없다** — 하는 것은 말 끝 감지(end-of-turn)이지 화자 식별이 아니다 (voice agent용). 모델도 `flux-general-en/multi` 뿐 (08/22 asyncapi 확인) |
| Whisper 계열 (오픈 가중치, 자체 호스팅) | **실시간 스트리밍이 아니다** — 배치 전용. 화자분리도 pyannote 등을 따로 붙여야 한다 |
| Whisper + pyannote 조합 | 화자분리를 후처리로 붙이는 구조라 **실시간이 성립하지 않는다** |
| HuggingFace · fal · Groq · OpenRouter 등 aggregator | 배치 전용이거나 실시간 화자분리 미지원. 프록시에서 접근도 막힘 |
| 브라우저 Web Speech API (ko-KR) | **화자분리·부스팅이 없다.** Field 앱의 P1 폴백으로는 남지만 판정 후보는 아니다 |

> 오픈 가중치 모델을 완전히 버린 것은 아니다 — 사내 이관 시 로컬 모델로 바꾸는 그림은 유효하고,
> 그때는 실시간·화자분리 요구가 달라질 수 있다. **해커톤 구현 범위에서만 탈락**이다.

## 7. 결정 후에 해야 하는 일

- 선택한 provider의 `apps/stt-lab/lib/stt/<provider>.ts`를 **`apps/field/lib/stt/`로 복사**한다.
  `app/page.tsx`는 비교 화면이라 **버리는 코드**다 — 이식 대상은 `lib/stt/`뿐이다.
- 키를 브라우저에 두는 방식은 랩 전용이다. Field에서는 **백엔드가 임시 토큰을 발급**하는 구조로 바꾼다
  (Soniox·Gladia는 그 API가 있고, Deepgram은 단기 키를 서버가 대신 쥐는 형태가 된다).
- 결정과 근거를 `docs/DECISIONS.md`에 기록하고, 소정에게 Field 연동 인터페이스를 넘긴다.
